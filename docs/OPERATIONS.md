# Локальный запуск и резервная копия

Текущий контур: один API-процесс, один Telegram-worker и SQLite `data/runtime/preview.db`. Сайт — `http://127.0.0.1:8001/`. Запуск: `scripts/start-web.ps1` и в отдельном процессе `scripts/start-telegram.ps1`. Они читают необходимые настройки из локального `.env`. Компьютер должен работать; постоянный сервер не настроен. Для восстановления процессов добавлен параметр `-KeepRunning` у обоих скриптов. Скрипт удерживает эксклюзивную блокировку и повторяет запуск дочернего процесса через пять секунд. Проверено восстановление сайта за 7,38 с и Telegram за 12,67 с, по одному логическому экземпляру каждой службы. Это не автозапуск после перезагрузки Windows. [Отчёт](reports/local-recovery-2026-11-14.json).

## Создание копии и проверка восстановления

Из корня репозитория в PowerShell:

```powershell
$env:PYTHONPATH='backend'
$env:PYTHONUTF8='1'
$env:DATABASE_URL='sqlite:///./data/runtime/preview.db'
.venv/Scripts/python.exe -m kurai.backup --destination data/runtime/backups/manual-001.db --restore-check data/runtime/restore-checks/manual-001.db --report work/backup-manual-001.json
```

Для каждого запуска нужны новые имена файлов базы. Без `--destination` создаётся имя с UTC-временем. Без `--restore-check` выполняется только копирование и проверка копии. Исходный путь берётся из `DATABASE_URL`, при отсутствии — текущий `preview.db`. Память SQLite и PostgreSQL этим способом не обслуживаются.

Используется online backup API SQLite, поэтому в копию попадают и подтверждённые данные из WAL; работающие процессы останавливать для создания копии не требуется. Существующий файл базы никогда не перезаписывается. Проверяются целостность, внешние ключи, числа строк всех таблиц и хэш логической выгрузки. Восстановление выполняется во **второй новый файл**, после чего результаты сравниваются. Отчёт содержит только агрегаты и хэш, без содержимого диалогов и идентификаторов пользователей.

Сами `.db` содержат рабочие данные, включая состояние подписок, и остаются в исключённой из Git папке `data/runtime/`. В репозитории публикуется только обезличенный отчёт. Автоматическая ротация файлов копий пока не реализована.

## Подтверждённая проверка 14 ноября

Перед расширением была проверена копия базы на 33 событиях. После загрузки регионов создана новая копия и восстановлен отдельный файл на **63 событиях**, с двумя подписками и 115 сохранёнными HTML-страницами. Целостность и связи корректны, логический хэш и числа строк совпали. Рабочая база не заменялась, восстановленный файл не подключался к боту и не отправлял уведомлений.

[Отчёт](reports/backup-restore-2026-11-14.json). Два коротких автоматических теста проверяют восстановление всех значений из работающей WAL-базы и отказ от перезаписи существующего назначения.

## Открытые пункты

Изолированная проверка не является полным сценарием аварийного переключения работающих процессов. Перед таким переключением нужно остановить оба процесса, выбрать проверенную копию, согласовать допустимую потерю более новых изменений, направить оба сервиса в одну восстановленную БД и проверить очередь уведомлений. Эти действия над текущей рабочей базой не выполнялись.

В изолированном Docker/PostgreSQL 16 проверены `pg_dump -Fc`, восстановление `pg_restore` в отдельную базу, совпадение строк и хэшей содержимого всех 14 таблиц. После остановки сервер восстановился политикой Compose за 9,23 с, данные сохранились. [Отчёт](reports/docker-postgres-2026-11-14.json). Это не аварийное переключение рабочей базы. Первичная сборка на новом томе прошла, но не засекалась; порог 10 минут не подтверждён.

Перед обновлением служб создана финальная копия SQLite: 65 событий, 181 исходная страница, две подписки; изолированное восстановление совпало. [Отчёт](reports/backup-restore-final-2026-11-14.json). Не публиковать сами базы — в них частные данные.
