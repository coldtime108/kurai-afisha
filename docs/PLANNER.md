# Планировщик «Выходной день»

Общий расчёт для сайта, Telegram и инструмента ИИ `plan_day`. Подбирает 2–4 опубликованных события одного города на выбранный день, проверяет время, возраст самого младшего участника и стоимость на всю группу. Расписание и суммы рассчитывает код по БД; модель разбирает свободный запрос.

## Как попробовать

На сайте открыть `/#planner` → «Спланировать день». В Telegram отправить `/plan` или выбрать «Спланировать день» после `/start`. Пошаговый сценарий работает без модели. Пользователь подтвердил живой проход Telegram 14 ноября.

Для текущих данных: **Стерлитамак, 15.11.2026, 2 взрослых, 10:00–22:00, без бюджета, одна площадка**.

| Событие | По времени Башкортостана | Основание окончания |
|---|---|---|
| «Царевна - Лягушка» | 12:00–13:00, прибыть к 11:45 | 60 минут в источнике |
| «Ужин с дураком» | 18:00–20:30, прибыть к 17:45 | 150 минут в источнике |

Оба спектакля — в русском драмтеатре Стерлитамака, ул. Худайбердина, 18. Переезд не нужен; между спектаклями остаётся 4 ч 45 мин до времени прибытия. Цены неизвестны, поэтому это предварительное расписание с пометкой «Нужны уточнения». При строгом бюджете маршрут не выдаётся за укладывающийся в сумму. Отдельная кнопка разрешает посмотреть варианты с неподтверждённой стоимостью.

Свободный запрос помощнику: «Составь план культурного дня на 15 ноября 2026 в Стерлитамаке: 2 взрослых, с 10:00 до 22:00, бюджет не задаю, только одна площадка». Затем: «Теперь свободны только с 17:00 до 22:00. Остальные условия сохрани».

## Ввод и результат

`POST /api/v1/planner/day`, контракт также в `/api/docs`. Минимальный ввод:

```json
{
  "city": "Стерлитамак",
  "day": "2026-11-15",
  "start_time": "10:00",
  "end_time": "22:00",
  "adults": 2,
  "children_ages": [],
  "budget": null
}
```

- `adults` и возраст каждого ребёнка: всего 1–30 участников, дети 0–17 лет. Возрастные маркировки проверяются по самому младшему.
- `budget` — рубли на всю группу. По обычному билету на каждого, включая детей; скидки и наличие мест не предполагаются. Это отличается от фильтра каталога по нижней цене одного билета.
- `max_events`: 2–4, по умолчанию 3. Возвращаются до трёх альтернатив.
- `arrival_buffer_min`: запас на вход, по умолчанию 15 минут.
- `max_transfer_min`: допустимый переезд, по умолчанию 45 минут.
- `transfer_minutes`: пользовательская оценка времени между разными площадками. Без неё соединяются только события с совпадающим известным адресом.
- `transfer_cost`: оценка расходов всей группы за один переезд, по умолчанию 0. Оценки пользователя явно обозначаются; дорожный маршрут не проверяется.
- `allow_unconfirmed_cost`: по умолчанию false. При заданном бюджете разрешение на варианты с неподтверждёнными ценами пользователь даёт отдельно.

Статусы: `ready`, `provisional`, `no_plan`. Ответ содержит фактический ввод, участников, временную шкалу, прибытие, длительность/время окончания и основание, переезды, свободные промежутки, диапазон стоимости, допущения, препятствия и предложения. Время — с часовым поясом, интерфейс отображает UTC+5.

## Правила расчёта

1. Только опубликованные будущие события нужного города и дня. Черновики и отменённые не участвуют.
2. Неизвестные возраст и длительность исключаются; конец не придумывается. Начало с запасом на вход и конец должны попадать в окно.
3. Предыдущее событие должно закончиться до прибытия на следующее с учётом указанного переезда. Переезд больше выбранного предела исключается.
4. Диапазон билета умножается на число участников, добавляются расходы на каждый переезд между разными адресами. Неизвестная цена не становится нулём; бесплатность должна быть явно указана.
5. Строгий бюджет требует известной верхней суммы, не превышающей бюджет. При явном разрешении неизвестных цен сохраняется предварительный статус; известная нижняя часть всё равно не может превышать бюджет.
6. Если маршрут не найден, показываются препятствия и подходящие отдельные события. Для известной стоимости предлагается минимальная найденная верхняя сумма; для узкого окна — минимальное найденное расширение, сохраняющее прочие условия. При недостатке данных предлагается уточнение. Условия сами не меняются.

Перебор ограничен 120 исходными событиями, 20 000 комбинаций и тремя результатами. Это ограничение работы алгоритма, не квота запросов ИИ. При неполном переборе ответ явно сообщает, что отсутствие маршрута не доказано или другие варианты могут быть лучше. Среди найденного выше идут варианты с большим числом событий, затем подтверждённые, с меньшей верхней стоимостью и меньшими промежутками.

## Проверки 14 ноября

- Семь новых автоматических тестов: состав/бюджет, неизвестная цена, возраст/длительность/отмена, переезды, пересечения/окно, Telegram без модели, инструмент ИИ с нормализованными условиями. После доработки подсказки окна эти семь тестов повторены.
- Ещё три затронутые проверки: память помощника, кнопка примера Telegram и отсутствие собственных квот ИИ. Всего десять разных целевых проверок прошли; весь набор проекта повторно не запускался.
- TypeScript и производственная сборка React прошли.
- На живом HTTP API проверены четыре случая: два взрослых без бюджета, строгий бюджет, явное разрешение неизвестной цены, ребёнок 8 лет. Неверное окно возвращает 422. Каталог, виджет и схема API доступны.
- Два обращения к NVIDIA выбрали `plan_day`, сохранили город и состав при изменении окна. Время HTTP-ответов — 3422 и 4782 мс, всего 9241 учтённый токен. Это два примера разработки, не итоговый p95 и не независимая приёмка. Собственный тестовый диалог и его трассы удалены.
- [Отчёт HTTP и модели](reports/planner-2026-11-14.json). После доработки подсказки окна отдельный HTTP-случай записан в этом же отчёте.

## Границы

Карты, пробки, географические маршруты и подтверждение наличия билетов не подключены. Между разными площадками используется только явно указанная оценка пользователя. После [регионального расширения](REGIONS.md) в каталоге 44 опубликованных сеанса в 13 городах; цены и длительности доступны не везде. Для многих дней честный результат — отсутствие маршрута из двух событий.

Пошаговый проход Telegram подтверждён пользователем. Автоматизированный просмотр нового интерфейса на desktop/360 px не выполнен: браузер чату недоступен, управление внешним браузером ранее остановлено политикой URL. Сборка не подменяет визуальную проверку. PostgreSQL/Docker, постоянное размещение и полные метрики ТЗ остаются отдельными пунктами.
